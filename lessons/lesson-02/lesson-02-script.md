现行讲稿共 29 页。与第 36 版 PPT 对应。P06 的整体网络图在 P07、P08 继续标注参数与专家。生成与 KV 部分使用同一请求、同一输出片段和同一执行布局。P10 的模板与 16 个 token 由目标模型的分词器生成，未加载模型权重。

## P02 H100 的计算单元与高带宽显存

### 屏幕展示

NVIDIA H100 SXM官方硬件产品图为主视觉。图上以编号定位GPU芯片（GPU Die）与高带宽显存（High Bandwidth Memory，HBM）。

- GPU芯片：内部计算单元（Compute Units）负责运算；计算能力称为算力（Compute Throughput）。
- HBM：保存数据；容量（Memory Capacity）表示可存多少，带宽（Memory Bandwidth）表示单位时间能传多少。

### 讲师脚本

“先看小智使用的H100这一类真实硬件。这里是NVIDIA官方的SXM模块产品图，不是常见带风扇的游戏显卡外形。”

“中央是一个GPU计算芯片（GPU Die）。H100 SXM的这个芯片内部启用了132个流式多处理器（Streaming Multiprocessor，SM），每个SM里还有CUDA Core与Tensor Core等运算单元。SM是芯片内部模块，不是独立die；周围封装上的长方形部件是HBM高带宽显存。显存保存数据，计算单元使用这些数据做运算。”

“周围的HBM是存储器堆栈，不是其他GPU计算芯片。一块卡也不普遍等于一个die，其他产品可能使用多die；本例专指H100。

“从这里引出三个量：显存容量是能存多少，显存带宽是数据能多快传到计算处，算力是计算部分能做多少运算。计算单元和缓存的内部细节，照片看不到，我们不在实物图上虚画芯片内部位置。”

### 图示与来源

[官方H100 SXM模块图片](materials/images/h100-sxm5.jpg)，来自[NVIDIA Hopper架构详解图1](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)。不把产品渲染图称为实拍。只定位可确认的芯片与HBM；接口背面在这张图中不可见，不作位置标注。

## P05 推理显存用在权重、KV Cache 和运行时空间

### 屏幕展示

承接上一页的 nvidia-smi，在显存读数右侧画三块并列的用途示意，不按比例绘制：

| 显存里放什么 | 小智的助手何时用到 |
|---|---|
| **模型权重（Model Weights）** | 模型启动时加载，查询 A1024 和其他订单共用这份权重 |
| **KV 缓存（KV Cache）** | 生成答复时保留已经处理过的上下文信息，供后续 token 使用 |
| **运行时空间（Runtime Memory）** | 推理过程中放临时张量、算子工作区和通信缓冲 |

### 讲师脚本

“把显存占用先拆成这三块。模型加载以后要把权重留在卡上。A1024 请求进入后，模型会保存已处理位置的 K、V，后面继续生成时还要用。执行过程中也需要临时空间。推理引擎也可能在启动时先为 KV 留好空间。图只说明用途，前面看到的 nvidia-smi 显存总量不能直接告诉我们每块占了多少。”

## P06 Qwen3 的各个模块如何处理订单问题

### 屏幕展示

用完整问题「订单A1024在哪？」贯穿。右侧从分词结果中摘出「订单」「在哪」「？」及其实际 ID。矩阵上的符号表示同一组位置经过不同模块后的状态。

| 模块 | 对理解问题或生成回答的作用 |
| --- | --- |
| 嵌入层 Embedding | 给各个 token 初始表示，让模型能区分「订单」和「在哪」 |
| 注意力 Attention | 把「在哪」和前面的订单信息联系起来 |
| 前馈网络 FFN | 加工已经汇入的线索，形成供后续层使用的表示 |
| 最终归一化 Final Norm | 把最终表示调整到适合输出层读取的尺度 |
| 输出层 Output Head | 根据已有内容判断接下来可能出现哪些 token |

### 讲师脚本

“我们还是用这个完整问题：订单 A1024 在哪？右上列的是其中几个 token，A1024 也在完整输入里。嵌入层给每个 token 一个初始表示。可以把矩阵的每一行看成模型为某个位置保留的信息。”

“‘在哪’单独看，没告诉我们在找什么。注意力让这个位置能结合前面的订单信息。前馈网络再加工汇入的线索，形成新的表示，交给下一层。图上 E、A、F 分别标出这些阶段，表示会随网络逐层更新。这里用订单问题帮助理解各模块的作用，图中连接和数值属于示意。”

“最后，归一化把这些信息的数值尺度调整好，输出层根据末位表示给接下来可能出现的 token 打分。打分变成概率之后，生成过程就可以选出一个 token，继续往下答。”

### 图示要求

右上先显示完整问题，再列出三个示例 token 和对应 ID。各功能示意与模块逐行对齐，保留带符号的矩阵。E → A → F 示意第一层，X 是 94 层之后的输出，hₜ 是完整输入的末位表示。P07 复用左侧网络位置。

## P07 Qwen3 的大部分参数集中在前馈网络

### 屏幕展示

复用 P06 的完整网络图，右侧并排显示每层参数和 94 层合计，单位为亿。注意力 0.71 → 67.0，前馈专家 24.16 → 2271.0。计入路由与归一化后，Transformer 层总计 24.88 → 2338.5。嵌入层和输出层分别约 6.22 亿。

总参数约235B；94层前馈模块合计约占97%。

### 讲师脚本

“图不变，我们把参数量贴上去。参数是训练得到的数字，通常组织成矩阵。矩阵可以先理解为按行列摆放的一张数字表；表里的数字要保存，使用它们时还要计算。”

“先按行比较。每层注意力约零点七一亿，九十四层共约六十七亿。专家每层约二十四点一六亿，九十四层共约二千二百七十一亿。算上路由和归一化，整个层堆叠约二千三百三十八点五亿。再加上嵌入、输出等层，就是整个模型的约二千三百五十一亿，也就是 235B。”

“现在能先解释显存的大头了。当前用BF16，每个参数两个字节，235B个参数的原始权重粗估约470GB。先记住这个关系：参数数量乘存储字节数。算完显存预算之后，我们再比较几种数值精度。”

“前馈模块占了绝大多数参数。是不是每个token都要把它们全部计算一遍？”

### 图示要求

完整复用 P06 网络图，原位加参数量，不切成条形图。右侧突出前馈总参数约97%、BF16原始权重约470GB；不把图形大小假装成计算量。

## P08 MoE 保留更多参数，每次只算一部分

### 本页只传递的信息

MoE保存很多专家，但每个token只选择部分专家参加计算。

### 屏幕展示

复用P06全网络，突出其中一层FFN并就地展开：Router → 128个Expert中的8个 → 汇总。

235B总参数关系到保存，A22B激活参数关系到每token的计算。

### 讲师脚本

“如果把前馈网络做得更大，每个 token 都经过整个前馈网络，计算量也会一起增加。混合专家（Mixture of Experts，MoE）让模型保留多组前馈参数，由路由器按当前 token 选一部分参与计算。我们把上一页的橙色模块展开看看。”

“小智的模型每层有128个专家，每个token选8个。图里只画几个代表，其余折叠。不同token可以走不同专家，这些专家是神经网络的参数，不是业务工具。”

“所以模型名里的235B与A22B不是同一件事：完整模型保存约235B参数，而单token约激活22B参数。只算一部分，不等于其余专家就不用保存。现在我们理解了权重显存的大头，接下来看看这些数字怎样产生回答。”

### 图示要求

保留Embedding、94层边界、Attention、Final Norm、Output原坐标。FFN外连放大区，路由与专家画在右侧；高亮被选专家，其他灰色。不得换成脱离网络的独立专家图。

## P11 从 JSON 请求到下一个 Token

### 屏幕展示

订单 A1024 示例。上排：请求 JSON → 聊天模板 → 分词器（16 个 Token ID）。下排：模型前向计算 → 输出层给词表打分 → 按生成策略选出「物流」。回箭头把选中的 Token ID 接回当前序列，再预测「延误」。

### 讲师脚本

“服务先取出 JSON 里的 messages。聊天模板加上角色、消息边界和助手回复的起始标记，分词器再把整段文本变成 16 个 Token ID。模型把这些 ID 转成向量，经过 Transformer，输出层用最后一个位置的表示给词表里的候选 Token 打分。”

“生成策略从候选中选出一个 Token ID，这里用‘物流’示意。解码器把这个 ID 转回可显示的文本，同时这个 ID 接到当前序列末尾，成为预测‘延误’时的上下文。API 只提交一次请求。”

## P12 无 KV Cache 时，生成「延误」要重算哪些位置？

### 屏幕展示

接回 P09 的前两步。原问题先生成「物流」，再把「物流」追加进去生成「延误」。放大第二步的注意力，用表格表示当前位置与各个词元的关系。蓝色是上一轮已经算过的格，橙色是加入「物流」后新增的格。

### 讲师脚本

“先回到 P09 的图。第一步问题进去，得到‘物流’。第二步把‘物流’接在问题后面，再预测‘延误’。我们打开第二步的模型框，只看注意力。”

“每一行是一个位置在看谁，每一列是它可能看的位置。比如‘在哪’可以看自己，也能回看前面的‘订单’。看右上角的灰格。模型生成答案时，某个位置只看自己和前文，因此旧位置看不到后来追加的‘物流’。这些格表示的关系就和上一轮一样。”

“如果每次都把完整前缀重新送过网络，蓝色三角会再算一次。橙色行才是这一轮新增的工作。回答越长，重复处理的前缀就越长。能不能直接沿用前一轮留下来的信息？”

### 图示要求

## P13 A1024 算例｜KV Cache 省下多少计算量？

### 屏幕展示

用课 1 订单 A1024 的第 7 次模型调用。输入含 12 个工具定义、历次工具调用和结果，共 2,448 token（离线分词）。假设这轮生成 256 token 的调查报告。

| 方案 | 处理位置 | 主要运算 | 8 卡峰值折算 |
| --- | ---: | ---: | ---: |
| 无缓存 | 659,328 | 30.24 PFLOP | 3.82 s |
| 复用历史 K、V | 2,703 | 0.125 PFLOP | 15.8 ms |

峰值折算少约 3.80 秒。实际 completion 耗时 = 首 token 耗时 + 后续 255 个 token 的生成时间。

### 讲师脚本

“刚才看的是 16 个 Token 的短请求。回到课 1 的实际项目，查完仓库、物流和政策之后，最后一次模型调用带着前几轮的工具调用和结果，也带着 12 个工具定义。我们把日志中这一轮的 JSON 按目标模型模板和分词器复算，得到 2,448 个输入 token。原 demo 的简短回答正文离线数出来是 45 个 token。这里假设客服需要更完整的调查报告，固定生成 256 个 token，比较同一输出长度。”

“按前文重算的方式，两种方案都先处理 2,448 个位置。之后无缓存每一步重算整个前缀，长度从 2,449 涨到 2,703。KV Cache 每步只让一个新位置过模型，但新位置的注意力仍要和前文配对。算上各层投影、专家和注意力配对，主要运算量从约 30.24 降到 0.125 千万亿次。”

“按 8 张 H100 的 BF16 稠密理论峰值折算，运算工作量的差值对应约 3.80 秒。15.8 毫秒是有缓存方案的峰值算力折算值。真正的服务要先产生第一个 token，再逐个生成剩余 255 个，每步还要读取权重和历史 K、V，以及进行多卡通信。因此实测要看首 token 和后续生成分别花了多久。”

### 讲师复算

设输入 N=2,448，输出 G=256。第一次处理 N 个输入产生第一个输出，随后处理 G−1 个新增位置。有缓存的处理位置数为 N+G−1=2,703。无缓存为 Σ(n)，n 从 N 到 N+G−1，合计 659,328。

令 T(n)=n(n+1)/2。无缓存每头配对为 ΣT(n)=850,078,336。有缓存每头配对为 T(N)+Σ(n)，后一个求和从 N+1 到 N+G−1，合计 3,654,456。

每层主要 FLOPs ≈ 2 × 活跃矩阵参数 × 处理位置数 + 4 × Q 头数 × 头维度 × 可见配对数。活跃矩阵参数为 71,303,168（Q、K、V、O 投影）+ 2,415,919,104 × 8/128（专家）+ 524,288（路由）= 222,822,400。使用 64 个 Q 头、头维度 128，乘 94 层并加上 256 次末位词表投影（每次 2 × 622,329,856）。估算省略归一化、激活、Softmax 等项。两种方案固定相同输入输出长度，也都只对每步末位做词表投影。

按 8 张 H100 SXM 的合计峰值 8 × 989.5 TFLOP/s 折算。这里比较一次 completion 内的历史 K、V 复用，输入仍需从头处理。这份日志来自教学 mock，输入与原答案正文长度是离线分词结果，GPU 延迟待实测。

## P15 小练习｜算出 KV Cache 省掉的工作量

### 屏幕展示

| 方案 | 物流 | 延误 | 了 | 。 | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 无缓存 | 16 | 17 | ？ | ？ | ？ |
| 有 KV Cache | 16 | ？ | ？ | ？ | ？ |

### 讲师脚本

“用 P09 那条订单请求做一个两分钟的计算。P10 已经数过，模型的输入有 16 个位置。我们固定输出这四个 token。先简化，每有一个位置要经过模型，就记 1 单位。算一下没缓存和有缓存时，生成四步各处理多少位置。”

## P16 KV Cache 的显存占用与解码读取带宽

### 屏幕展示

KV Cache 的两项资源开销是显存容量和读取带宽。每次生成新 token 时，还要从显存读取相关历史 K、V。

小智的模型按 BF16 缓存计算，每保留一个 token，需要 188 KiB 逻辑 KV。缓存 8K token 约 1.47 GiB，32K token 约 5.88 GiB。

### 讲师脚本

“前面我们省掉了把历史 token 再跑一遍的工作。但要用它们的 K、V，就得让这批数据留在显存里。输入更长、回复继续生成，缓存都会增长。对于小智的多轮 Agent，每次模型调用送进去的历史消息和工具结果，都会影响这轮请求的缓存规模。”

“还有一笔代价发生在每次生成。新 token 仍然要读历史 K、V。长上下文留下的缓存更大，每步要读取的历史数据也更多。所以我们要同时关心显存容量能留下多少，以及显存带宽能多快把数据送到计算单元。”

### 讲师复算

逻辑 KV 每 token = 2（K 与 V）× 94 层 × 4 个 KV 头 × 128 维 × 2 字节 = 192,512 B = 188 KiB。8K 为 8,192，32K 为 32,768。这里用逻辑 KV 量，部署时按分片、复制和引擎实际配置核对。

### 过渡

省掉计算以后，显存容量和读取带宽仍要核算。接下来观察单请求解码时还有没有余量处理其他请求。

“单个请求在解码时，一步只推进一个 token。能不能把多个请求的一步放在一起做，提高这台机器每秒能产出的 token？”

## P17 批处理提高解码吞吐量

### 屏幕展示

有缓存后，批大小为 1每步只让一个新位置过模型。算得少，但仍需读取参与本步的权重和历史 KV，GPU 算力可能有空闲。

| 同一轮解码 | 批大小为 1 | 批大小为 4 |
| --- | --- | --- |
| 每步处理的 Token 位置 | A | A、B、C、D |
| 权重 | 供一个位置使用 | 共享权重在同批次内复用 |
| 历史 KV | 读 A 的历史 | 分别读 A、B、C、D 的历史 |
| 每步生成 | 1 个 token | 4 个 token |

只要合批后的单步耗时小于单请求的 4 倍，整台服务每秒产出的 token 就更多。单请求的词元间延迟（ITL）可能变长。

### 讲师脚本

“回到 P15。没缓存时，为了预测‘延误’，整个前缀的 17 个位置都再跑一遍，各层的矩阵运算一次已经有多行可做。有缓存以后，只剩‘物流’这一行需要过各层。模型仍要读取这一步参与计算的权重，还有历史 K、V。工作量小了，GPU 的计算单元却可能因为等数据或输入矩阵太小而闲着。这个现象主要看单条或小批量解码。”

“把四条请求各自的新位置凑成一批，GPU 一次可以处理四行。它们仍分别读取自己的历史 K、V，所以一批的 KV 读取量比单条大。收益来自共享权重可以在一批里服务多个位置。对小智的 MoE，部分权重是共享的，不同请求还可能选不同专家，实际能复用多少要测。”

“我们比较两个时间。假设单请求 10 毫秒产出一个 token，批大小为 4 20 毫秒产出四个。单个请求两次输出之间反而等得更久，但整台服务从每秒 100 个 token 变成每秒 200 个。这只是说明怎么算吞吐。上下文很长时，KV 读取可能主导，批次变大后耗时也可能接近按请求数增长，吞吐收益就会缩小。”

### 讲师备注

可以用一个带宽受限的简化模型补充。令 W 是这一步四条请求都用到的权重数据量，K 是单条请求要读的历史 KV。四条请求分别算约读 4W + 4K，理想合批约读 W + 4K。这个对照假设四条等长、共享权重能在同批复用，省略不同专家的权重、其他数据及开销。K 占比越大，合批少读权重带来的比例收益越小。生产判断同时看吞吐、首 token 和后续 token 间隔。

### 使用材料

[NVIDIA 矩阵运算性能指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)。

### 过渡

“合批有机会多产出，但也要同时存下并读取更多 KV。接下来看看显存和时延各自能让我们把批次做多大。”

## P19 为四路并发估算显存和 GPU 张数

### 屏幕展示

服务最大上下文设为 8,192 token（输入＋已生成），按 4 条并发都到上限做容量预算。权重和 KV 用 BF16。

- **权重** = 参数量 × 每参数字节数 = 235B × 2 字节 ≈ 470 GB。
- **KV** = 并发 × 服务最大上下文长度 × 每 token KV。
  - 每 token KV = 2（K 和 V）× 保存逐 token KV 的层数 × 每层 KV 头数 × 每头维度 × KV 存储字节数。
  - 小智的模型：4 × 8,192 × [2 × 94 × 4 × 128 × 2 字节] ≈ 6.3 GB。
- **运行时与余量**：课堂统一按（权重 + KV）× 20% 预留。

初步预算：（470 + 6.3）× 1.2 ≈ 571.6 GB。按每卡 80 GB，向上取整得到 8 张，再核对逐卡占用。

### 讲师脚本

“刚才给定显存算并发。现在业务给了我们目标：同一时间接四条，服务把每条请求的最大上下文设为 8K，输入和已生成输出都算在内。先算整个副本要存下什么。权重四条请求共用一份，参数量乘每参数的字节数。”

“KV 则按请求增加。括号里的 2 是 K 和 V，94 是保存逐 token KV 的层数，4 是每层的 KV 头数，128 是每头维度，最后的 2 字节是 BF16 缓存精度。算出单 token 的大小之后，乘并发和部署配置的最大上下文，按每条都到上限做预算。实际请求的缓存占用按当时已缓存的长度计算。”

“权重和 KV 之外，运行时还要空间给临时张量、算子工作区和通信。选卡时先用一个课堂假设，把权重和 KV 的总量再加 20%。这样得到约 571.6 GB，除以 80 GB 再向上取整，先按 8 张卡规划。”

“20% 是第一轮预算用的系数。不同模型和引擎的实际缓冲有固定开销，也会随批次变化。确定分片方案之后，用引擎报告和代表性负载的峰值校准。”

### 讲师备查

整机初估先用逻辑 KV。八卡方案假设权重均摊且 KV 复制两份，则每卡权重约 58.75 GB、KV 约 1.58 GB。按同一课堂系数再算一遍，每卡预算约 (58.75 + 1.58) × 1.2 = 72.4 GB。配置可行性仍需逐卡核对。

同为 1 并发、32K、FP16，用同一规则比较。Qwen3-0.6B 的权重约 1.20 GB、KV 约 3.76 GB，预留约 0.99 GB，合计约 5.95 GB。Qwen3.6-27B 文本路径的权重约 54 GB、标准 KV 约 2.15 GB，预留约 11.23 GB，合计约 67.38 GB。27B 混合架构的线性注意力状态实际部署时另行核算。

## P20 显存估算公式与所需参数

### 屏幕展示

把小智四路并发算例中的数字擦掉，保留三个算式：

- **权重** = 总参数量 × 每参数字节数
- **KV Cache** = 并发 × 最大上下文长度 × 2（K 和 V）× 保存逐 token KV 的层数 × 每层 KV 头数 × 每头维度 × 每个 KV 数值的字节数
- **课堂显存预算** =（权重 + KV Cache）× 1.2，额外 20% 作为运行时和余量的初估

图下放两组来源。**模型提供**：总参数量、保存逐 token KV 的层数、KV 头数、头维度。**部署设定**：权重和 KV 的精度、最大上下文、并发目标和预留。

### 讲师脚本

“换模型时，先把需要的数字分两组。总参数量、层数、KV 头数和头维度，要去查模型资料。并发和最大上下文是服务要支持的目标，精度和预留是部署方案的一部分。先合计权重和 KV，再加运行时空间。课堂用 20% 粗估，实际要用引擎的启动报告和压测校准。”

## P21 同样多的参数，位宽决定存储大小

### 屏幕展示

**显存大小，不只取决于参数数量**

| 数值表示 | 每个数的存储位数 | 保存10亿个数的原始空间 |
|---|---|---|
| FP32 | 32 bit | 4 GB |
| FP16 / BF16 | 16 bit | 2 GB |
| FP8 | 8 bit | 1 GB |
| INT4 | 4 bit | 0.5 GB |

**位数更少，占用更小，数值表示也有取舍。**

### 讲师脚本

“要做显存预算，得先知道每个权重或 KV 数值要存几个字节。参数本质上是数字，但计算机保存一个数字，可以使用不同的格式。比如同样十亿个数，每个数用四个字节，就要四GB；每个数用两个字节，就要两GB。”

“这里一个字节是八个bit。FP32用三十二位，FP16和BF16都用十六位，所以后面算显存时，它们都是每个数两个字节。但FP16和BF16的数值范围、精细程度并不一样，不是同一种格式。”

“位数减少，能够表示的数值范围或者间隔也会变化。可以借助尺子理解：刻度有限时，一些数只能用附近的值近似。这个比喻解释表示误差，不代表所有数值格式的刻度都是均匀的。”

“把已有数字转成更低位宽的近似表示，是量化（Quantization）的基本思路。它可能减少空间和数据搬运，也可能引入误差；能否提高速度，还取决于硬件和实际执行方法。不是在配置里随便改个名字，模型就一定更小、更快。”

“小智当前按BF16存权重，235B个参数乘两个字节，原始权重粗估约470GB。这里还没有计算其他空间，也不是完整部署容量。”

“前面算过的 KV，也是计算产生的数字。权重用什么格式，KV用什么格式，是两件可以分别讨论的事。课3再看服务怎样选择和验证。”

### 图示要求

以同样数量的数据格为基准，展示4、2、1、0.5倍GB的同比例空间差异，标签保留中英文：数值格式（Data Type）、位宽（Bit Width）、量化（Quantization）。不画成同一种二进制编码的简单截尾，不承诺质量不变或速度按位数同比提升。

### 讲师备注

本表是十进制GB的原始数据大小，实际量化还可能有缩放因子、分组元数据与对齐开销。INT4是整数表示，不与FP8混称同一种“浮点精度”。权重、激活（Activation）和KV可采用不同配置，本课不展开量化算法、校准、内核或具体vLLM配置。本页回答数值存储问题，不恢复独立的权重换算练习页。

## P24 两卡张量并行算例｜一步解码汇总 128 次

### 屏幕展示

按上一页的课堂公式，Qwen3-32B 约需 89 GB，超过单卡 80 GB。接下来用两卡部署看通信开销。两卡张量并行，64 层，32 条请求各生成一步，隐藏维度 5,120，BF16。假设采用每层两次 All-Reduce 的经典切分。

1. 两张卡各算一个部分结果，经 All-Reduce 相加，两张卡都拿到汇总结果。
2. 每次处理的张量大小 = 32 × 5,120 × 2 字节 = 320 KiB。若两卡直接交换部分结果，每卡发送 320 KiB、接收 320 KiB。
3. 一步解码有 64 × 2 = 128 次汇总，每卡累计发送 40 MiB、接收 40 MiB。若每次汇总用 12 µs，且不与计算重叠，合计约 1.54 ms。

### 讲师脚本

“模型按张量并行拆到两张卡后，看两张卡各自算出的结果，每张卡只算了其中一部分，但结果张量还是 32 行，每行 5,120 个 BF16 数。两张卡需要交换并求和，各自拿到下一步所需的完整结果。这个操作叫 All-Reduce。”

“经典的切法在注意力和前馈各汇总一次，所以每层两次，一步解码 64 层就要 128 次。这里用两卡直接互换来数，每卡发送 40 MiB、接收 40 MiB。也就是说，单次消息不大，反复同步也会积累时间。”

“如果这种消息大小下，一次汇总耗时 12 微秒，而且都在关键路径上，算出来约 1.54 毫秒。这是课堂假设。部署时要按实际拓扑、并行切法、消息尺寸和通信重叠情况测。NVLink 或 IB 的标称带宽，无法单独给出这个时间。”

### 使用材料

[经典张量并行切法](https://research.nvidia.com/labs/adlr/MegatronLM/)、[Qwen3-32B 配置](https://huggingface.co/Qwen/Qwen3-32B/blob/main/config.json)。

## P26 能处理请求，意味着成功率和延迟达标

### 屏幕展示

| 要确认什么 | 看什么 |
|---|---|

## P27 Prefill 和 Decode 对应不同的延迟指标

### 屏幕展示

时间轴上先画请求到达，再画输入预填充（Prefill）和三次后续解码（Decode）。首 token 耗时（TTFT）从请求到达到「物流」出现，包含排队等服务开销。后续 token 间隔（ITL）分别是「物流 → 延误」「延误 → 了」「了 → 。」。

### 讲师脚本

“刚才定义能接住请求时，除了成功率和吞吐，还看 TTFT 和 ITL。回到 A1024 的示例，沿时间轴看这两个指标分别受什么影响。请求到达后可能排队，随后模型进入 Prefill。它一次处理多个已知输入位置，建立各层 KV，从输入末位选出第一个 token‘物流’。从到达到这里，就是首 token 耗时。”

“后面是 Decode。‘物流’作为新位置进入模型，读取已有 KV，生成‘延误’；再用‘延误’生成‘了’。这些相邻输出的间隔，对应用户看到回答持续出现的节奏。”

“Prefill 一次有更多输入位置要计算，长输入时容易增加首 token 的等待。小批量 Decode 每步算的位置少，但反复读取所需权重和历史 KV，还可能等卡间交换。哪一部分先跟不上，要结合真实长度和批次测量。”

### 图示要求

同一条时间轴上，蓝色输入方块进入 Prefill，橙色 Decode 依次推进。第一段标 TTFT，后续段标 ITL。用淡色标出可能排队，图形长度只示意顺序。

### 过渡

“压测如果先看到首 token 等太久，就从排队和 Prefill 查起；如果首字正常但后续输出断断续续，就重点看 Decode。最后把这一课的判断串起来。”
