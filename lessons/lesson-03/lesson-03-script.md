## P03 从订单到 GPU 的四种并行分工

### 屏幕展示

| 层级 | 图里放什么 | 到下一层的分工 |
|---|---|---|
| 1 订单请求 | A、B、C、D | **DP 数据并行（Data Parallelism）** 把订单分到不同模型副本 |
| 2 模型副本 | 两份完整模型，展开第一份 | **PP 流水线并行（Pipeline Parallelism）** 把模型的 Transformer 层分给前后两段 |
| 3 Transformer 层 | 展示前后两段各负责哪些层，高亮第 2 层 | 展开第 2 层，看里面的计算模块 |
| 4 层内模块 | Attention 注意力和 FFN 前馈网络，FFN 用 MoE 专家示意 | **TP 张量并行（Tensor Parallelism）** 分注意力头组；**EP 专家并行（Expert Parallelism）** 分专家 |
| 5 GPU | GPU 1 持有头组 A、专家 A，GPU 2 持有头组 B、专家 B | 每张卡的 HBM 存所分配的权重和 KV，SM 执行计算 |

### 讲师脚本

“从图顶跟着订单 A 往下走。A、B 去模型副本 1，C、D 去模型副本 2。DP 分的是订单。展开模型副本 1，前一组 GPU 算前段的层，把中间结果交给后一组。PP 分的是模型里的层。”

“接下来只看第 2 层。输入先过 Attention，再过 FFN。这张图里的 FFN 由 MoE 专家实现。蓝色是 Attention 的两组头及对应的 Q、K、V 投影权重。下面两张 GPU 各算一组，输出投影时汇合。这是 TP，拆的是同一层里的张量。”

“橙色是 MoE。专家 A、B 分别放在两张 GPU 上。图中路由器给这个 token 选了 B，GPU 2 上的专家 B 做这部分计算。这是 EP，按专家分工。实际 MoE 可以选中多个专家，EP 分组也可以跨 DP 组。图里展示的是开启 EP 的教学示例。小智每台八卡机器用 TP=8，由外部网关在 12 个独立模型副本之间分流。八卡基线的专家 FFN 也按 TP 切分。”

如果学员问普通 FFN 能不能用 TP：“可以。以两张卡为例，普通 FFN 的中间维度可以平分。每张卡只存和计算自己的中间通道，升维后在本卡做激活，降维时各自算一份输出贡献，再把两份加起来。每个 token 都走两张卡，合起来完成同一个 FFN。”

### 图示要求

一页画完整的五层。用连线从订单指到模型副本，从模型副本指到 PP 的两组 Transformer 层。高亮第 2 层并展开 Attention 与 FFN／MoE，最后用蓝色和橙色把两种模块的分工对应到同一对 GPU。左侧只放 DP、PP、TP、EP，按各自对应的连接位置对齐。图中沿连线标「展开第 2 层」。

### 实操与产出

请学员从订单 A 指到第 2 层，再分别指出头组 A、B 到哪张卡算，以及图例中被选中的专家到哪张卡算。

### 使用材料

[vLLM 并行策略](https://docs.vllm.ai/en/stable/configuration/optimization/#parallelism-strategies) · [vLLM 专家并行](https://docs.vllm.ai/en/stable/serving/expert_parallel_deployment/#layer-behavior-with-ep-enabled) · [八卡案例配置](materials/serve-case.yaml) · [Qwen3 MoE 实现](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/models/qwen3_moe.py) · [Qwen3 普通 FFN](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/models/qwen3.py#L976) · [FFN 的 TP 实现](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/models/qwen2.py#L1339)

## P04 推理引擎把模型变成可调用的服务

### 屏幕展示

**推理引擎把磁盘上的模型变成可调用的服务。**

启动时：模型目录 → 加载模型与分词器 → 权重放到 GPU

运行时：助手请求 → 模板与分词 → 排队、合批与 KV 管理 → GPU 推理（Prefill 与 Decode）→ 返回文本或工具调用

### 讲师脚本

“P02 的权重、结构配置和分词器由推理引擎读取。启动时，引擎按上一页图里的分工把模型加载到 GPU。服务起来之后，订单助手发模型 API 请求。图以 GPU 为例，后面的 CPU 小练习沿用同一套 API。”

“一个请求进来，先用聊天模板和分词器准备输入，再排队。调度器决定这一轮安排哪些请求，管理它们的 KV 空间，然后交给 GPU 执行。Prefill 处理输入，Decode 逐步生成。最后把文本或工具调用返回。模型如果提出查物流，助手执行工具并带着结果再问。”

“后面每个优化都可以回到图上定位：合批改实例内调度，模型副本分流改请求去向，前缀缓存省掉重复计算。”

### 图示要求

## P05 vLLM 和 SGLang 的调度与缓存特点

### 屏幕展示

**两款开源推理引擎，都能把模型部署成 API。**

**vLLM**：PagedAttention 按块管理和读取 KV；支持多种模型与 Attention 后端。

**SGLang**：RadixAttention 复用相同前缀的 KV；Model Gateway 按缓存和负载分流。

### 讲师脚本

“vLLM 的代表设计是 PagedAttention。KV Cache 按块分配，序列增长时可以继续取块。不同请求内容各不相同，也能各用各的 KV 块。现在的 vLLM 还会按硬件和模型选择 Attention 计算后端，例如适用 GPU 上的 FlashAttention。”

“SGLang 用 RadixAttention 组织共享前缀，已有 KV 时可以跳过相同开头的计算。它的 Model Gateway 还能参考模型副本上的缓存和负载来路由。两者都有前缀缓存，这里用代表性设计帮助大家理解。”

### 图示要求

左边画两条不同请求各指向一组 KV 块。右边画两个相同开头指向共享 KV。术语与图形对齐。

### 实操与产出

让学员区分按块分配 KV 与跨请求复用前缀。

### 使用材料

[PagedAttention 论文](https://arxiv.org/abs/2309.06180) · [vLLM Attention 后端](https://docs.vllm.ai/en/latest/design/attention_backends/) · [RadixAttention 论文](https://arxiv.org/abs/2312.07104) · [SGLang Model Gateway](https://docs.sglang.io/docs/advanced_features/sgl_model_gateway)

## P11 用在途请求数和吞吐估算平均延迟

### 屏幕展示

**稳态下，平均端到端延迟 ≈ 平均在途请求数 ÷ 实测吞吐**

| 指标 | 并发 8 | 并发 12 |
|---|---:|---:|
| 平均在途请求数 | 8 条 | 12 条 |
| 实测吞吐 | 4 条／秒 | 5 条／秒 |
| 平均端到端延迟 | 8 ÷ 4 = 2.0 秒 | 12 ÷ 5 = 2.4 秒 |

本表在每个并发档持续供给请求，表中的在途数和吞吐来自同一稳态窗口。

### 讲师脚本

“假设用同一批类型的请求压测，完成一条就补一条。平均在途 8 条时，测得每秒 4 条。把平均在途提高到 12 条，测得每秒 5 条。并发增长得比吞吐快，平均端到端延迟就从 2 秒增加到 2.4 秒。”

## P18 连续批处理｜调整 max-num-seqs，观察吞吐和排队

### 屏幕展示

**vLLM 默认用连续批处理。max-num-seqs 是每轮序列数上限。**

课堂八卡基线 `max-num-seqs: 32`，候选 `max-num-seqs: 64`。

**优化场景** 运行序列经常到 32，等待队列在涨，KV 池还有余量。

**调参风险** 设得过高会让更多序列同时占 KV，可能触发抢占与重算，也可能拉长生成间隔。

**验证与回退** 看实际批次、P95 TTFT／ITL、抢占和达标吞吐。吞吐持平或延迟超线就回退。

保持 max-model-len: 32768、max-num-batched-tokens: 4096 和订单流量不变。

### 讲师脚本

“把运行序列数和等待队列放在一起看。只有运行数经常到 32、队列在涨，同时 KV 池还有空间，才值得试着调大运行名额。客户端并发也包括排队的请求，所以要从服务端确认实际运行数。”

“vLLM 的常规 `vllm serve` 调度器内置连续批处理，启动服务就采用这种方式。YAML 里的 `max-num-seqs` 对应命令行 `--max-num-seqs`，限制一次调度迭代可处理的序列数。它只给上限，实际批次还要看有多少请求、这一轮的 token 数上限和 KV 空间。API 队列可以有更多请求在等。”

“课堂八卡基线显式设 32，这是起点配置。未显式设置时，由 vLLM 按版本、设备和运行方式选择默认值。确定运行序列数多次碰到 32 且还有资源，再把 `serve-case.yaml` 复制一份，候选只改为 64，固定 `max-model-len: 32768`、`max-num-batched-tokens: 4096` 和订单流量。最后比较达标吞吐、P95 TTFT 和 KV 抢占。”

“在 /metrics 同时看 running、waiting、KV 池使用率与抢占增量。若队列在涨但运行数不到 32，先找 token 数上限、KV 或算力限制。单纯把上限提到 64 并不能让每轮跑满。若运行数变多但 KV 逼近容量，抢占和重算可能抵消收益。这个八卡案例在 P13 用 P95 TTFT ≤ 500 ms、P95 ITL ≤ 60 ms、P95 E2EL ≤ 5000 ms 和成功率 ≥ 99% 判断是否达标。”

## P21 分块 Prefill｜调整每轮 token 上限，兼顾短查和长调查

### 屏幕展示

**max-num-batched-tokens：一次调度迭代中最多处理的 token 数。**

这一轮处理的输入 token 和生成 token 一起算。

### 讲师脚本

“max-num-batched-tokens 用一个更直白的说法就是每轮最多处理多少 token。举例，这一轮 4 条回复各推进 1 个 token，同时长调查读入一段新输入。这两部分算在同一个上限里。支持分块的 vLLM V1 会先安排生成，再用剩余空间处理长输入。”

“把 4096 改成 2048，只是对照起点。短查询更顺，长调查首字更慢，都有可能。两组固定相同的长短请求配比、上下文上限和序列上限。这里从八卡配置的 32 个序列名额出发。若长调查超出门槛，回退或试中间档。”

## P40 KV 预算与抢占｜出现抢占且指标变差时，再调整 KV 预算

### 屏幕展示

**KV 池默认自动估算。小智把每卡推理显存预算显式设为 90%。**

| 显存还有余量 | 显存余量不足 |
|---|---|
| 小步提高 gpu-memory-utilization | 降低 max-num-seqs，少放几条请求同时跑 |

**优化场景** 长调查高峰反复抢占，P95 延迟或达标吞吐同时变差。峰值达标就保留基线。

**调参风险** 显存预算太高可能 OOM，运行名额太低可能让队列变长。

**验证与回退** 回放同一批高峰请求，看 KV 使用率、抢占增量、P95 延迟和达标吞吐。OOM 或延迟超线就回退。

### 讲师脚本

“vLLM 的 KV 池默认自动估算。小智的八卡 YAML 显式设置了 gpu-memory-utilization 为 0.90，指每张卡的推理显存预算比例。vLLM stable 的 serve 文档列 0.92，较早版本如 v0.15.1 列 0.90。以部署版本的文档和配置为准。”

“权重和运行开销占掉一部分预算，KV 池用余下的空间。比如假设一张卡有 80 GiB，按 90% 先得到 72 GiB 推理预算，再扣掉假设的 63 GiB 权重和运行开销，约剩 9 GiB 给 KV。这个算例只说明比例与池容量的关系。实际部署看启动日志的 GPU KV cache size，以及按最大请求长度估算的 Maximum concurrency。kv-cache-memory-bytes 默认留空。如果显式设置，就按每 GPU 的字节数指定 KV 池，覆盖基于显存比例的自动估算。”

“生产中没有统一比例说明多少部署需要调这项。先用常态和峰值订单跑基线。短输入、低并发，或者峰值依旧达标，就继续用当前配置。长历史、高并发、卡上权重占得多时，更容易撞上 KV 容量。看每个模型副本在峰值窗口内的 KV 使用率曲线（vllm:kv_cache_usage_perc）和抢占次数增量（vllm:num_preemptions），再对照 P95 TTFT、P95 ITL、P95 E2EL 和达标吞吐。一次短暂的抢占，或者 nvidia-smi 看起来快满了，先和业务指标一起判断。”

“如果代表性高峰反复抢占，而且尾延迟或达标吞吐受影响，再做对照。显存确有余量时，小步加 GPU 预算。余量不足时，先试把 max-num-seqs 从课堂基线 32 往下调。每次只改一项，检查启动、峰值稳定性和队列是否变长。”

上方明确区分 KV 池自动估算和小智的 90% 显存预算。下面展示两条可选操作，以及先观察哪些指标再决定是否调参。

| P/D 分离 | 分块后长输入仍干扰出字 | 读输入与生成拆到两组 | 交接耗时、两侧队列、ITL |
| 模型副本分流 | 一边排队，另一边还有余量 | 模型副本路由规则 | 每台队列、集群吞吐 |
