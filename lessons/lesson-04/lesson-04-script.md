## P03 先算每次调用，再合计整单 API 费用

### 屏幕展示

**单次费用 =（未命中输入 × 未命中单价 + 命中输入 × 命中单价 + 输出 × 输出单价）÷ 1,000,000**

**A1024 这一轮的模型 API 费用 = 同一条执行轨迹中各计费模型调用步骤的费用之和**

| 例子费率 | 未命中输入 | 命中输入 | 输出 |
|---|---:|---:|---:|
| 美元 / 百万 token | 0.30 | 0.006 | 1.20 |

### 讲师脚本

“每个 token 只进它在本次调用所属的那一栏。输入总量是前两栏之和。模型生成工具名和参数也属于输出，虽然客服界面看不到。工具查回来的内容，送入下一次模型请求时，计入那次调用的输入。我们按服务商的用量口径算。把 A1024 这一轮里的七个模型调用步骤加起来，得到这一轮费用。遇到计费的重试，也要计入。”

“输入命中和未命中是两类用量。第 2 课讲过 KV Cache，服务如果能复用已计算的前缀，这部分输入可以按命中价算。这里用服务返回的命中数来区分两类。”

“这张费率表用的是 DeepSeek Flash 的高峰公开价。课堂固定这套费率，好比较不同请求的费用。”

### 讲师备注

用第 2 次调用代入：（413 × 0.30 + 1,024 × 0.006 + 35 × 1.20）÷ 1,000,000 = 0.000172044 美元。

### 过渡

“其余六次用同一个公式。下面请 WorkBuddy 帮我们把整份账本算出来。”

[DeepSeek 官方定价，2026-11-10 核对](https://api-docs.deepseek.com/quick_start/pricing/)

## P04 小练习｜用 WorkBuddy 算出 A1024 的 API 费用

### 屏幕展示

**输入**　逐次调用的 token 用量与三个费率  
**先算基线**　按给定用量计算每次调用和整单费用  
**再算理论最低成本**　固定调用次数、输入与输出 token 数和费率，假设全部输入命中缓存

### 讲师脚本

“第 1 课统计了这七次调用的用量。给大家 6 分钟，请 WorkBuddy 写一个小计算器，用第 1 课会话 JSON 的 teaching_usage.calls 和刚讲的公式把它算成费用。需要验算程序时，可以用练习材料里的简化任务核对。核对命中输入加未命中输入等于总输入，逐个模型调用步骤计算费用，再汇总到这一轮。教学用量中的 `turn` 字段是原项目里的模型循环序号，七行都属于同一轮对话。”

“再算一个理论最低成本。调用次数、输入与输出的 token 数和费率都不变。如果每个输入 token 都按更低的缓存命中价收费，最低能到多少？也可以反过来算一次全未命中，看看费用差多少。”

### 产出

一份可复用的本地计算器、A1024 的逐次费用明细，以及固定用量下的理论最低成本。

## P05 小练习讲评｜基线与输入全命中的费用

### 屏幕展示

用横向堆叠条形图展示三类费用占整单费用的比例。标出各类 token 数和对应的美元金额。

| 计费类别 | token | 美元 |
|---|---:|---:|
| 未命中输入 | 3,109 | 0.000933 |
| 命中输入 | 9,216 | 0.000055 |
| 输出 | 380 | 0.000456 |

**教学基线 0.001444 美元/单 → 理论最低 0.000530 美元/单（输入全命中）**

旁边按执行轨迹顺序排列七个模型调用步骤的横向用量条，保留 token 刻度，供后续优化页对照。

### 讲师脚本

“把 12,325 个输入 token 全按命中价算，再加上 380 个输出 token 的费用，得到 0.00052995 美元。这是固定用量下的理论下限，实际能命中多少要看服务返回的 usage。即使输入全命中，输出还是要付 0.000456 美元。除了提高命中率，小智还可以减少调用次数、减少读写的 token，或者让适合的步骤走费率更低的模型。”

如果学员也算了输入全未命中的情景，核对结果为 0.0041535 美元/单。

把逐次账本和整单基线留给本课后面的应用优化。自建案例沿用第 3 课的服务配置，比较达标任务吞吐与能否释放计费资源。

### 屏幕展示

|---|---|
| **减少模型调用次数** | 一次响应提出两个工具、应用先查订单、封装订单和物流查询 |

## P12 应用预取订单｜由应用先查订单，再把结果交给模型

- **用户输入**　调查 A1024。

- **工具结果**　A1024、运单 TA1024、承诺 2026-10-28 送达。
- **模型收到订单**　优化前到第 2 次模型调用才读到订单结果。优化后第 1 次模型调用就带订单结果，决定后续调查。

## P15 封装订单与物流查询｜把订单和物流查询封装成一个工具

### 屏幕展示

页眉：方法 3 · 优化思路

再次以原始七次调用为对照。模型给出订单号，组合工具在内部完成两步查询。

- **用户输入**　调查 A1024。
- **模型决策**　优化前第 1 次调用 `get_order({"order_id":"A1024"})`，第 3 次调用 `get_tracking({"tracking_number":"TA1024"})`。候选改为一次 `get_order_tracking({"order_id":"A1024"})`。
- **工具内部**　程序先通过订单号查订单，再取返回的运单号查物流。
- **工具结果**　一次返回订单详情与 TA1024 物流轨迹，下一次模型调用继续查仓库和政策。

`get_order_tracking` 是待实现的候选新工具。保留末尾的物流复查，工具失败时返回明确错误。

### 讲师脚本

“第三种方案从原始七次调用出发。模型仍然决定何时调用工具，程序负责工具内部的两步查询。查物流确实要等订单工具返回运单号，但拿到运单号以后，如何查物流是固定的。我们可以把这两步封装成一个工具，让模型只需要给订单号。”

“这里的 get_order_tracking 是准备新增的候选工具。它内部仍然查两个系统，返回订单和物流两份结果。原来的第二次查询仓库依然要做，末尾要求的物流复查也依然要做。我们只是把固定的传参和衔接交给程序，减少模型在中间决定下一步的次数。”

“封装时要保留两次查询的原始结果和错误来源。订单不存在时停止这条链，不继续查物流；物流超时时保留已取到的订单证据，并按业务规则重试或升级。这里展示候选方案，具体调用次数和费用由实现后的完整回放确定。”

## 选讲

- **长会话压缩（Compaction）。** 例如调查跨了多次追问，后续只传带来源和时间的事实表与未解决问题，原记录留存。核对政策条件和冲突证据有无遗漏，把摘要开销和缓存变化计入整单。[Claude Compaction 文档](https://platform.claude.com/docs/en/build-with-claude/compaction)
- **调低推理强度（Reasoning Effort）。** 仅适用于支持该设置的模型。把已核实事实整理成客服答复时，可测试低档位，分别核对实际输出用量、业务验收和回退。第 1 课的 Qwen Instruct mock 用于演示流程。[DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)
- **终止无效循环。** 如果同一轮的执行轨迹显示反复调用相同工具、参数相同且结果无变化，增加业务终止条件，并设模型循环次数上限作兜底。仍需保留有业务意义的物流复查。这个方法在异常回放中演示更合适。
- **缓存工具结果。** 例如在相同权限和有效期内复用同版本政策。若把缓存结果照常发送给模型，收益主要在工具调用，模型用量仍以实际 usage 为准。
- **离线 Batch API。** 把夜间工单分类或质检等可延后任务交给服务商的异步批量接口。按供应商规则核算折扣与处理时限。[Claude 批量处理文档](https://platform.claude.com/docs/en/build-with-claude/batch-processing)
